# Queue And Stability

## 为什么要做全局排队限流

RAG 对话和传统 CRUD 接口不一样，它是长连接、流式输出、链路长、资源消耗高。如果不对并发进行约束，最容易出现的问题不是单次请求失败，而是线程池、模型连接、Redis、下游网络资源被一起拖垮，最后表现成雪崩式 RT 抬升和 SSE 连接堆积。

## 当前方案

项目通过 Redis、Lua、ZSET 和服务端本地控制组合实现全局排队限流。核心思路是：

1. 进入请求先排队，避免瞬时洪峰直接压到模型链路。
2. 用 Redis 原子脚本保证 claim 行为一致，减少并发竞争下的脏状态。
3. 在排队之外再做执行许可控制，避免同一时刻活跃 SSE 过多。
4. 配合会话记忆压缩，降低长对话对 Token 和内存的累积压力。

## 压测时该看什么

- `QPS`
  单节点每秒完成的请求数。

- `RT`
  一次 SSE 请求从发起到完成的总耗时。

- `TTFB`
  首包返回时间，更能体现排队、检索和首轮模型响应速度。

- `P95`
  观察长尾请求，面试里非常常问。

- `成功率`
  统计 HTTP 正常返回且 SSE 正常完成的请求比例。

- `稳定性`
  例如压测 10 分钟内无 OOM、无线程池拒绝、无服务重启。

## 简历表达方式

不要只写“做了限流”，更建议写成：

“基于 Redis + Lua + ZSET 实现全局排队限流与 SSE 资源保护，在 X 并发、X 次请求压测下单节点稳定支撑 X QPS，平均 RT X ms，P95 X ms，测试期间无 OOM 和服务雪崩。”
